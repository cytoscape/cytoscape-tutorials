Integrate the Web with Cytoscape + NDEx

  • Your applications live in the browser; the network analysis still lives in Cytoscape Desktop.
  • Two pieces of infrastructure enable this integration:
    • CyREST
    • NDEx
  • Three integration patterns you'll see:
    1. Push a network from a web app into Desktop ("Open in Cytoscape")
    2. Persist networks in NDEx — then hand the same network to Cytoscape with one call
    3. Embed an interactive network directly in Cytoscape Web

Many bioinformatics workflows begin in a browser-based tool — a portal, a dashboard, a gene-set analysis interface — and at some point users need to transfer results into Cytoscape for detailed network analysis. Previously this required exporting and re-importing files. With CyREST and the CX2 format, the transfer reduces to an HTTP call. NDEx also plays a role here: beyond serving as a public network repository, it can function as a persistence layer for web applications, since it natively supports CX2 — the same format Cytoscape imports. The js4cytoscape monorepo provides the JavaScript libraries for these interactions.

The @js4cytoscape Monorepo

  • Talk to Cytoscape Desktop
    • @js4cytoscape/js4cytoscape — wrapper over CyREST providing cyBadge(), commandsPOST(), cyrestGET()
  • Talk to NDEx (and use it as your backend)
    • @js4cytoscape/ndex-client — TypeScript client for the NDEx v2/v3 REST API.
  • Work with CX / CX2 data
    • @js4cytoscape/cx2js — convert legacy CX → cytoscape.js

Six packages organized into three functional groups. The first is js4cytoscape itself — the programmatic interface to Cytoscape Desktop. The second is ndex-client, a TypeScript client for the NDEx REST API. Notably, ndex-client serves two roles: it provides standard REST operations (search, upload, download, authentication), and it also includes CyNDExService, which transfers CX2 networks to a locally running Cytoscape instance. This means the same CX2 format used for storage in NDEx is directly importable by Cytoscape, requiring no format conversion. The remaining four packages provide CX2 type definitions and converters for rendering networks in the browser with cytoscape.js. Today's demo uses only js4cytoscape and ndex-client.

The "Open in Cytoscape" Pattern (and Where NDEx Fits)

  • The transfer requires three calls to http://127.0.0.1:1234:
    1. cyBadge() — is Cytoscape running? (status badge on the page)
    2. CyNDExService.postCX2NetworkToCytoscape(cx2, title, collection) — push the network
    3. commandsPOST("layout hierarchical") etc. — execute Cytoscape commands remotely
  • The CX2 payload can originate from various sources — inline JSON, a query result, or an NDEx network UUID.

The implementation consists of a static HTML file loading two libraries from a CDN. When the user triggers "Open in Cytoscape," the page serializes a CX2 network and POSTs it to Cytoscape's local REST endpoint via CyNDExService. Once received, it becomes the active network in Cytoscape, and subsequent CyREST commands can apply layouts, adjust views, or save sessions. The commandsPOST function supports any command available in Cytoscape's Command Line interface. In this demo the CX2 is defined inline, but in a production application the same payload would typically be retrieved from NDEx via NDExClient. The workflow follows the pattern: detect → fetch (optionally, from NDEx) → push → command.

Why Cytoscape Web?

  • Browser-based deployment. Cytoscape Web runs in the browser, requiring no local installation.
  • This lowers the barrier to access for: classrooms, collaborators, tablet users, and restricted computing environments.
  • the integration bridge changes:
    • With Desktop, the bridge was localhost (CyREST)
    • With Web, the bridge is URLs — either a network already in NDEx, or any CX2 file the browser can fetch
  • As a result, NDEx (or any HTTP-accessible host) serves as the intermediary between a web application and Cytoscape Web.

The Desktop integration requires a local Cytoscape installation, which can be a barrier for some users — students, reviewers, collaborators on unfamiliar machines, or tablet users. Cytoscape Web eliminates this requirement by running in the browser. The architectural difference: with Desktop, the integration point was a REST endpoint on localhost. In the browser, there is no equivalent local endpoint — one tab cannot push data to another. Instead, the integration mechanism becomes a URL. The network must reside at a location Cytoscape Web can fetch — either an NDEx repository or any HTTP-accessible CX2 file. This makes NDEx particularly central in the Web integration model, as it provides both persistence and a standard retrieval interface.

Three Ways to Integrate with Cytoscape Web

  1. Open any CX2 file from a URL (simplest, no auth needed)
    • Host a CX2 file anywhere the browser can reach → link to https://web.cytoscape.org/?import=<encoded-cx2-url>
  2. Open an NDEx network by UUID (for apps with user accounts)
    • Your app saves a network to NDEx → redirects to https://web.cytoscape.org/0/networks/<uuid>
  3. Cytoscape Web App API (live inside Cytoscape Web)
    • Your code runs as a Cytoscape Web app — custom panels, analyses, UI extensions — with direct access to the network model

Three patterns, distinguished primarily by the degree of coupling. The first two are external: the web application remains in its own browser tab and passes a network to Cytoscape Web via a URL. The third is internal: application code runs within Cytoscape Web itself. For most web applications, the first two patterns are sufficient, as they maintain separation between the application UI and Cytoscape Web. Use the ?import=URL pattern for public datasets, tutorials, or example networks where no user state is involved. Use the NDEx UUID pattern when users have accounts and require persistence and sharing — NDEx provides these capabilities. The App API is appropriate when the tool needs direct access to the network model — for custom layout algorithms, domain-specific analysis panels, or specialized views. That approach involves tighter coupling and is outside the scope of this tutorial.

The Pattern Behind the Demo

  • Both buttons resolve to the same mechanism: a URL. The integration reduces to a hyperlink.
  • The difference is where the CX2 lives at the moment the user clicks:
    • Button 1: CX2 sits at a public URL → URL contains ?import=... → Cytoscape Web fetches it
    • Button 2: Network sits in NDEx → URL contains the UUID → Cytoscape Web fetches from NDEx
  • The same URL can also carry view state (panels open/closed, selected nodes, active tab) — useful for deep-linking from reports, papers, and email.

The key observation is that the integration mechanism is a URL — no SDK instrumentation or authentication handshake is required. The user follows a link and the network opens in Cytoscape Web. The two patterns differ only in what the URL references. In pattern 1, the network resides at an HTTP-accessible URL, and Cytoscape Web imports it via a query parameter — this requires only a window.open call, no library. In pattern 2, the network is stored in NDEx; the URL carries its UUID and Cytoscape Web retrieves it from NDEx. In a production application, the UUID would be generated by ndex-client when saving the user's network — this demo uses a pre-existing network, but the save code is shown on the page for reference. Additionally, the URL can encode view state parameters for precise deep-linking.
